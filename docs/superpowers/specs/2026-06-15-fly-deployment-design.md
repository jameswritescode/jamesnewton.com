# Fly.io Deployment — Design Spec

**Date:** 2026-06-15
**Status:** Approved (pending written review)
**Branch context:** `phoenix-migration` (deploys run from this branch's checkout)

## Overview

Make the Phoenix app deployable to Fly.io as a single-machine app in **`lax`**,
backed by the user's existing **"Personal" Managed Postgres** cluster and a
**persistent volume** for uploaded photos. The work is purely additive
infrastructure: a release `Dockerfile`, `.dockerignore`, release entrypoint
scripts, and a hand-written `fly.toml`. The application code needs **no changes**
— `config/runtime.exs` already reads everything from the environment
(`DATABASE_URL`, `SECRET_KEY_BASE`, `PHX_HOST`, `PORT`, `PHX_SERVER`) and sets
`media_root` to `/data/images` in prod — and `lib/newton/release.ex` already
provides `migrate/0` and `create_admin/2`.

### Goals

- A reproducible production image built via `mix release` (no Mix at runtime).
- One-command deploy (`fly deploy`) that runs migrations automatically.
- Uploaded photos persist across deploys (volume at `/data/images`).
- Connect to the existing MPG cluster with a **dedicated database + least-priv
  user** for this app.
- A clear runbook for the Fly CLI steps the user runs.

### Non-goals (this pass)

- Custom domain `jamesnewton.com` (deferred follow-up: `fly certs` + DNS +
  flip `PHX_HOST`).
- Object storage for photos (a volume is used; revisit if scaling out).
- CI/CD via GitHub → Fly (deploys are manual `fly deploy` for now).
- Horizontal scaling / multiple regions (single machine, because the volume is
  pinned to one machine).

## Locked decisions

- **Region:** `lax` (co-located with the user's LAX Managed Postgres).
- **App name:** `jamesnewton-com`.
- **Database:** existing "Personal" MPG cluster, with a **dedicated database**
  (`newton`) and a **dedicated app user** (not the admin `fly-user`); attach sets
  `DATABASE_URL`.
- **Photo storage:** Fly **volume** `media` mounted at `/data/images`
  (matches `media_root`). **Single machine** (`min_machines_running = 1`,
  no scale-out) since volumes aren't shared.
- **Custom domain:** deferred; `PHX_HOST = "jamesnewton-com.fly.dev"` for now.
- **Artifacts via** `mix phx.gen.release --docker` (Dockerfile/.dockerignore/rel
  scripts), `fly.toml` hand-written.

## Architecture

### Why a release (not Mix in prod)

`mix release` produces a self-contained artifact bundling ERTS + compiled BEAM +
deps, shipped in a slim runtime image **without** Mix. Migrations and admin
creation run through the release's `bin/newton eval` calling `Ecto.Migrator`
directly (`Newton.Release.migrate/0`) — not `mix ecto.migrate`. This keeps the
image small and is the standard Phoenix prod pattern.

### Files to generate (the codebase work)

1. **`Dockerfile`** — multi-stage:
   - **Builder** (`hexpm/elixir:<ver>-erlang-<ver>-debian-<rel>` or the
     generator's pinned base): install build deps, `mix deps.get --only prod`,
     compile, `mix assets.deploy` (digests static assets), `mix release`.
   - **Runtime** (slim Debian): copy the release, run as a non-root user, expose
     the port, `CMD ["/app/bin/server"]`.
   - Generated by `mix phx.gen.release --docker`; reviewed to confirm the
     Elixir/OTP/Debian versions match the project and that `assets.deploy` runs.
2. **`.dockerignore`** — excludes `_build`, `deps`, `node_modules`, `.git`,
   `priv/static/assets` build output, test/doc dirs, the local `screenshot.mjs`,
   etc., for a small, clean build context.
3. **`rel/overlays/bin/server`** — sets `PHX_SERVER=true` and execs
   `bin/newton start` (the endpoint only starts when `PHX_SERVER` is set, per
   `runtime.exs`). Baked into the image at `/app/bin/server`.
4. **`rel/overlays/bin/migrate`** — runs `bin/newton eval
   'Newton.Release.migrate()'`. Baked in at `/app/bin/migrate`; used as the
   `release_command`.
5. **`fly.toml`** — hand-written:
   - `app = "jamesnewton-com"`, `primary_region = "lax"`.
   - `[build]` → uses the Dockerfile (`dockerfile = "Dockerfile"`).
   - `[env]` → `PHX_HOST = "jamesnewton-com.fly.dev"`, `PORT = "8080"`.
   - `[http_service]` → `internal_port = 8080`, `force_https = true`,
     `auto_stop_machines = "stop"`, `auto_start_machines = true`,
     `min_machines_running = 1`.
   - `[[mounts]]` → `source = "media"`, `destination = "/data/images"`.
   - `[deploy]` → `release_command = "/app/bin/migrate"`.

### Verification of the app side (no changes expected)

- `runtime.exs` (prod block) reads `DATABASE_URL` (raises if missing),
  `SECRET_KEY_BASE` (raises if missing), `PHX_HOST`, `PORT`, enables IPv6 socket
  options for the DB when applicable, and sets `media_root` to `/data/images`.
- Confirm `PORT`/`PHX_HOST` line up with `fly.toml` (`8080` / the fly.dev host).
- Confirm the MPG `DATABASE_URL` host works with the configured
  `socket_options` (IPv6 over the Fly private network); adjust only if the MPG
  URL format requires it.

## Deploy runbook (Fly CLI steps the user runs)

These require authenticated `flyctl` and touch the account, so the user runs them
(inline with `! fly …` so output returns, or independently).

1. **Create the app (no deploy):** `fly apps create jamesnewton-com`.
2. **Create the media volume in LAX:**
   `fly volumes create media --region lax --size 1 -a jamesnewton-com`.
3. **Dedicated db + user on the existing MPG cluster:**
   - `fly mpg databases create` → create `newton`.
   - `fly mpg users create` → create an app user scoped to `newton`.
   - **Attach:** from the cluster's Connect tab (or flyctl) attach
     `jamesnewton-com` using that user/db so `DATABASE_URL` is set to the
     least-privileged app credentials (not the admin `fly-user`).
4. **Set the app secret:**
   `fly secrets set SECRET_KEY_BASE="$(mix phx.gen.secret)" -a jamesnewton-com`.
5. **Deploy** (from the `phoenix-migration` checkout): `fly deploy` — builds the
   image, runs `release_command` (migrations) on a temporary machine, boots
   `/app/bin/server`.
6. **Create the admin login:**
   `fly ssh console -a jamesnewton-com -C "/app/bin/newton eval 'Newton.Release.create_admin(\"hello@jamesnewton.com\", \"<strong-password>\")'"`.
7. **Verify:** `https://jamesnewton-com.fly.dev` → `/login` → exercise the admin;
   upload a photo to confirm the volume persists it; confirm the public pages
   render.

### Custom domain (deferred follow-up)

`fly certs add jamesnewton.com`, add the A/AAAA (or CNAME) records Fly prints,
then set `PHX_HOST = "jamesnewton.com"` in `fly.toml` and redeploy.

## Error handling / risks

- **Volume = single machine:** durability relies on Fly volume snapshots, not
  replication; no horizontal scale. Acceptable for a single-admin blog; revisit
  with object storage if needed.
- **Release command failure** (e.g. a bad migration) aborts the deploy before the
  new version goes live — old machine keeps serving.
- **Missing secrets** (`SECRET_KEY_BASE`/`DATABASE_URL`): `runtime.exs` raises at
  boot with a clear message; set them before `fly deploy`.
- **Asset build:** `mix assets.deploy` must succeed in the image; the Dockerfile
  installs the JS toolchain (esbuild/tailwind via the Elixir wrappers — no Node
  needed since the project uses the `esbuild`/`tailwind` Hex packages). Confirm
  during implementation that the image builds assets without Node.

## Testing approach

Infra has no unit tests; verification is operational:
- `docker build .` succeeds locally (image builds, assets digest, release
  assembles) — a fast local check before involving Fly.
- `mix precommit` stays green (no app code changes expected).
- Post-deploy smoke per the runbook step 7 (login, upload, public pages).

## Unit breakdown

- `Dockerfile`, `.dockerignore` — release image + clean build context.
- `rel/overlays/bin/server`, `rel/overlays/bin/migrate` — release entrypoints.
- `fly.toml` — app/region/volume/release-command config.
- (Reference only, already present) `config/runtime.exs`, `lib/newton/release.ex`.
